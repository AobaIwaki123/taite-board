# ADR-0005: 静的JSON配信の継続方針とAPIサーバー化の条件

## ステータス
Accepted

## 決定日
2026-10-30

## 対象コンポーネント
- `data/generated/schedule.json`
- `k8s/manifests/`
- `deploy/nginx.conf`
- GitHub Pages / Cloudflare

## 背景と課題
Webやモバイルアプリ向けのバックエンドを検討する際、一般的なアプローチとしてはデータベース（PostgreSQLやMongoDB）とREST/GraphQL APIサーバー（Node.js, Go, Python等）を構築・常時稼働させることが多い。
しかし、本プロジェクトの特性を考慮した場合、早期のAPIサーバー化およびDB導入はオーバーエンジニアリングとなり、運用の複雑性を不要に増大させる懸念がある。

## 決定事項
1. **静的JSONファイル配信（Static JSON Distribution）の徹底継続**:
   - クライアント（Web、ネイティブアプリ）への配信形式は、生成された静的ファイル `schedule.json` のみをCDNまたは静的Webサーバー（Nginx / GitHub Pages / Cloudflare）から配信する。
   - バックエンドに常時稼働するデータベースや動的APIプロセスを配置しない。
2. **キャッシュバスターとデータ鮮度の管理**:
   - クライアント側で `fetch('schedule.json?t=' + Date.now())` またはHTTP ETag / Cache-Controlヘッダーを活用し、ブラウザキャッシュによる更新遅延を防止する。
3. **動的APIサーバー化へ移行する明確なトリガー条件（すべてを満たさない限り移行しない）**:
   - **条件1 (ユーザー認証・認可)**: ユーザーごとのマイページ、お気に入り・推しメン登録、通知設定などの個別状態をサーバー側に保存する必要が生じた場合。
   - **条件2 (秒単位の双方向・動的リアルタイム同期)**: ライブ会場の現在進行状況（例: 「今1曲目終わりました」「特典会列締切」など）を現場から秒単位で投稿・反映する要件が生じた場合。
   - **条件3 (トランザクション処理)**: チケット予約の代行や決済、整理券配布など、サーバーサイドでの原子性と排他制御が必要になった場合。

## 採用理由と設計根拠
- **圧倒的な可用性と耐障害性**: 静的配信はDBダウン、コネクション枯渇、サーバープロセスクラッシュ、メモリリークといった障害要因が原理的に存在しない。
- **インフラコストの極小化**: Kubernetes環境においても最小限のNginxコンテナ（またはCloudflare Pages等のエッジCDN）だけで数万〜数十万リクエストを難なく捌くことができる。
- **メンテナンスフリー**: データベースのマイグレーションやセキュリティパッチ適用作業が不要。

## 検討した代替案と却下理由
- **最初からGo / PostgreSQLによるREST APIサーバーを立ち上げる**:
  - 却下理由: 現状の読み取り専用（Read-heavy）なスケジュール閲覧ユースケースに対して、費用・運用保守・障害監視コストが釣り合わない。

## 影響範囲とリスク
- **静的ビルド時間**: スケジュールが更新された際、Go CLIでJSONを再生成して配信ストレージ（またはコンテナ内）へ配置する更新ラグ（数秒〜数十秒）が発生する。
