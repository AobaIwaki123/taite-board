# TODO-05: lumitree を利用した TimeTree 公開カレンダーの自動取り込み

- **ステータス**: 実装済み（デプロイ後の CronJob 動作確認待ち）
- **目的**: 対象グループの公開カレンダーを定期取得し、個別イベント URL の手入力を減らす。
- **前提**: TODO-02 の決定論的 Upsert と競合時の対象指定を利用する。

## 現状

- `internal/source/timetree/` は、指定されたイベント URL を lumitree のイベント一覧から探して取得し、見つからなければ公開ページの OGP を参照する。カレンダー全体の定期巡回ではない。
- 対象はリボンクロックの `ribbon_clock` と Dolly Kiss の `lui_17707`。前者はユーザーから指定された ID であり、`data/groups.json` の空欄を更新する。
- lumitree は `GET /api/v1/calendars/{id}/events?year=YYYY&month=MM` でイベント一覧を提供する。ページングや対象月の扱いは実装前に実 API と仕様を確認する。
- `.agents/skills/taite-timetree-sync/SKILL.md` は確定済み情報を上書きしない手動同期の手順を定めている。

## 検討・実装項目

1. `timetree_id` が設定されたグループを対象に、lumitree から定期取得し、取得結果を現在日から翌々月末までに絞る。実 API は月パラメータを指定しても複数月を返すため、カレンダーごとの一覧を取得する。対象・期間の入力と取得・同期処理を分離し、グループとページは順次処理する。
2. カレンダー ID とイベント ID を取得元の識別子として保持し、同じ予定を再取得しても重複を作らない。日時変更など安全に反映できない変更は競合としてログに残す。
3. TimeTree イベントの開始時刻を無条件でライブ出番に使わず、本文中の出番・特典会・会場・チケット等を判定可能な範囲で抽出する。終日予定や時刻未定は推測で補わない。
4. 既存の確定済み時刻・会場・特典・チケット等は自動で上書きせず、未入力欄の補完に限る。TODO-02 の複数候補による競合は勝手に選択せず、対象指定が必要な候補として残す。
5. 元予定の削除、キャンセル、日時変更を検知した場合の扱いは、既存の確定情報への影響が大きいため運用方針を決めてから実装する。取得失敗を削除と誤認しない。
6. 定期取得した内容は安全に特定できる範囲で自動反映し、曖昧な候補は確認待ちとする。実行結果、取得件数、変更・競合・失敗を CronJob のログから確認する。
7. 実際の GCS 正本への保存、既存の取得・正規化処理との接続、再実行時の動作、認証・権限と必要なリソースを確認する。実行時間より費用の抑制を優先し、並列処理や不要な AI 呼び出しを避け、既存基盤を優先する。

- [x] 確定済み情報を保護し、未入力情報だけが補完される。複数候補では自動的に公演を選ばない。
- [x] 終日・時刻未定、複数ページ、本文形式の違い、API エラーと世代競合をテストする。

- [ ] CronJob の稼働と公開データへの反映をデプロイ後に確認する。削除・日付変更の自動反映は行わず、日付変更は競合として記録する。

実行ログは `kubectl logs -n ribonclock -l job-name=<job-name> --all-containers` で確認する。`kubectl get jobs -n ribonclock` で実行名を確認できる。
