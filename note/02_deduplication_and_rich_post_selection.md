# 名寄せ（Deduplication）と情報量最大ポスト選定アーキテクチャ

## 1. 概要と背景

アイドルグループのライブスケジュール運用において、同一の公演に対して複数のX（旧Twitter）ポストが発信される。具体的には以下のライフサイクルが存在する。

| 投稿フェーズ | 発信時期 | 主な内容 | 情報特性 |
|---|---|---|---|
| チケット一次告知 | 2〜4週間前 | 日程、会場、開場/開演、チケット発売日、券種・価格 | チケットURL、開催概要が確定。タイテや撮可曲は未定 |
| 主催・イベンター告知 | 1〜2週間前 | 全出演者ラインナップ、全体タイムテーブル画像 | 全体画像はあるが、グループ個別の指名特典や詳細ブースは不明 |
| 前日・直前詳細告知 | 前日夜〜当日朝 | グループ出番時間、並行/終演後物販ブース、撮可曲（曲順・曲名） | 現場行動に直結する確定テレメトリー情報がすべて揃う |
| メンバーによる引用・告知 | 随時 | 個人意気込み、自撮り写真、チェキ予約の呼びかけ | 構造化データとしては断片的 |

同一日付・同一会場のイベントに対してこれらが個別に収集された場合、単純に後勝ちや先頭優先で上書きすると「チケットURLはあるがタイテがない」、あるいは「タイテはあるがチケットURLが消失する」といった情報の欠落が生じる。
したがって、ポスト間の「名寄せ（同一イベント判定）」と、AIまたはルールベースによる「情報量スコアリング（最も密度の高いポストの選定と統合）」が不可欠となる。

## 2. 名寄せ（同一公演判定）の照合アルゴリズム

同一イベントか否かを判定するキーは以下の3点である。

1. **公演日（Date）の一致**:
   - 年月日（YYYY-MM-DD）が完全一致すること。
2. **会場（Venue）の類似度**:
   - 表記ゆれ（例: 「渋谷RING」と「SHIBUYA RING」、「O-nest」と「Spotify O-nest」）を正規化辞書または文字列距離（Levenshtein距離 / Jaro-Winkler距離）で照合。
3. **部制（Session）の整合性**:
   - 同日2回し（昼帯・夜帯 / 1部・2部）が存在する場合、開場・開演時刻またはセッション区分（1部/2部）により分離。

## 3. 情報量スコアリング（Richness Scoring）の設計

同一イベントと判定されたポスト群の中から、どのポストを基盤とし、不足情報をどのポストから補完するかを決定するための重み付け指標を定義する。

| 評価項目 | 配点 | 判定基準 |
|---|---|---|
| タイムテーブル画像（Image OCR / Flyer） | +40点 | 画像URLが存在し、出演時間表・タイテが視覚化されている |
| 出番・物販時間の明記（Telemetry Times） | +25点 | 「出番 XX:XX〜」「特典会 XX:XX〜」「ブース名」が含まれる |
| 撮影可能ルールの確定（Photo Rule） | +20点 | 「○曲目『曲名』」など具体的な楽曲指定・撮影条件が含まれる |
| プレイガイドURL（Ticket URL） | +15点 | TicketDive, LivePocket, TIGET, イープラス等のURLが含まれる |
| 指名入場特典の明記（Admission Bonus） | +10点 | 「お目当て特典」「指名特典」などの記載がある |
| 公式アカウント（Official Source） | +10点 | `@Ribbon_Clock` 等の公式発信アカウントである |

### スコアリングによる統合（Merge & Backfill）ルール
1. **プライマリソースの選定**: 最もスコアの高いポストを代表レコード（`primary_session`）とする。
2. **バックフィル（Backfill）処理**: プライマリレコードで欠損しているフィールド（例: 直前告知にチケットURLの記載が省略されていた場合）は、過去のチケット告知ポスト（セカンダリレコード）から自動的に補完する。
3. **元ソースリンクの保持**: 各公演データには、判定根拠となったXポストのURL（`source_tweet_url`）を必ず紐付け、利用者が一次情報を即座に追跡できるようにする。

## 4. 撮影可能（撮可）情報の取り扱いと防御設計

アイドル現場において撮影レギュレーションの誤認はファンと運営・会場間の重大なトラブルにつながる。
分析の結果、リボンクロックにおいては「前日夜の直前告知ツイート」においてのみ「○曲目『曲名』」という形式で撮可曲が発表される運用が確認された。

したがって、以下の安全原則を適用する。
- **推測補完の厳禁**: 「一般的に静止画は撮れるだろう」といった推測による `allowed: true` や「静止画のみ可能」の自動付与を禁止する。
- **明記なしの非表示（Fail-Safe）**: 公式ポストに「曲目」「『曲名』」の記述がない場合は、未定（`null`）として扱い、UI上の表示枠ごと非表示とする。
