# X（Twitter）起点のライブスケジュール自動収集における構造的課題と解決設計

## 1. 概要と発見された事実

地下アイドル・ライブアイドルのスケジュール情報基盤を構築する過程において、**「グループ公式Xアカウントのポストのみを巡回するクローラーでは、重要なライブ出演情報が確実に漏落する」** という事実が判明した。

具体例として、2026年11月7日（土）に開催される大型対バンイベント **「MARQUEE祭 mini Vol.355」（会場：渋谷 Spotify O-nest）** では、出番（17:40〜18:00）や並行物販（18:10〜19:10 ブースA）、プレイガイド（イープラス）といった重要情報が、グループ公式の通常テキスト告知ではなく、**主催者側が発行したフライヤー画像1枚の中にのみ集約**されていた。

本ノートでは、なぜX単体のクローリングで情報が欠落するのか、その構造的ボトルネックを整理し、将来的な完全自動化アーキテクチャの指針を策定する。

---

## 2. X依存クローリングにおける4大ボトルネック

### 2.1 主催者主導イベントにおける告知情報の画像閉じ込め
対バンイベント（フェス・オムニバス形式）では、タイムテーブル全体の決定権がイベント主催者（雑誌編集部、制作会社、イベンター等）にある。
主催者は全出演者のタイテを1枚の画像（フライヤー）にまとめて公式アカウントから発信するため、以下の現象が発生する：
- 主催者ポストにはテキストとして各グループの出番・物販時間が記載されず、「詳細は画像をチェック」で済まされる。
- グループ公式アカウントはそれを引用RT（リポスト）するだけで、自アカウントからプレーンテキストで出番を発信しないケースが多い。

### 2.2 公式ポスト本文の文字数制限とoEmbed APIによる切り捨て
X（Twitter）の長文ポストであっても、外部連携API（oEmbed API）を通すと約280文字でテキスト末尾が切り捨てられる（`…` によるTrancation）。
アイドル現場のポストは「イベント名 → 日時 → 会場 → 特典内容 → チケットリンク」の順に書かれるため、末尾の最も重要なプレイガイドURL（TicketDive, TIGET, LivePocket, イープラス）が消失する。

### 2.3 プレイガイド（チケ発サイト）の分散
アイドルのチケット販売元は単一ではなく、主催者ごとに異なるプラットフォームが使われる：
- [TicketDive (チケットダイブ)](https://ticketdive.com/)
- [TIGET (チゲット)](https://tiget.net/)
- [LivePocket (ライヴポケット)](https://t.livepocket.jp/)
- [イープラス (e+)](https://eplus.jp/)
- 主催専用予約フォーム（Google Forms, Formzu等）

グループ公式の告知が漏れている場合、これらプレイガイド側でグループ名検索をかけないと公演の存在自体を検知できない。

### 2.4 直前確定カルチャー（前日・当日のタイテ画像流し込み）
対バンイベントは出演者の体調不良や機材トラブル等による時間変更が頻繁に発生するため、公式タイムテーブル画像が前日の夜〜当日の朝に投稿されることが多い。事前クローリングのキャッシュが古いまま現場を迎えるリスクがある。

## 3. 今後の解決アーキテクチャ指針

X公式アカウント単体への依存を脱却し、以下の多層データ収集パイプラインを構築する。

| 収集レイヤー | 対象ソース | 抽出手法 / 役割 |
|---|---|---|
| **Layer 1: グループ公式X** | `@Ribbon_Clock` 本文・メディア | 基本ポストの監視、FxTwitter API経由での全文取得 |
| **Layer 2: フライヤー画像OCR** | ポスト添付画像、主催画像 | Vision LLM / OCRによるタイムテーブル枠・出番・物販の自動パース |
| **Layer 3: 主催者アカウント監視** | `@MARQUEE_matsuri` 等の主催者X | グループ名メンションやリポスト元画像の逆引き追跡 |
| **Layer 4: プレイガイドAPI/検索** | TicketDive, TIGET, eplus | グループ名キーワードによる日次イベント巡回 |
| **Layer 5: 手動・人間介在（HITL）** | 本画面のような画像直投 | ファンや運営がフライヤー画像を直接投入できるフォールバック口 |
