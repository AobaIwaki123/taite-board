# X告知自動巡回・多段前処理フィルター・昇格パイプライン詳細設計書

## 1. システム全体概要

本設計は、アイドル公式Xアカウント（告知ポスト）からのスケジュール自動収集を実現しつつ、無関係なツイートによるコスト高騰や誤判定を排除するための、**「自宅k8sヘッドレス巡回 ＋ 3段ローカルフィルター ＋ Cloud Run AI解析 ＋ 半自動昇格」**のEnd-to-Endアーキテクチャを定義する。

### 1.1 全体パイプラインの流れ

~~~text
+-----------------------------------------------------------------------------------+
| 自宅 Kubernetes クラスタ                                                          |
|                                                                                   |
|  [ CronJob: taite-crawler ] (1日2回: 12:00, 22:00)                               |
|       │                                                                           |
|       ├── 1. Playwright Headless Chromium 起動                                   |
|       │      └── https://x.com/<group>/media へアクセス                           |
|       │      └── GraphQL /UserMedia 通信を横取りしてポストメタデータを回収        |
|       │                                                                           |
|       ▼                                                                           |
|  [ 多段ローカル前処理フィルター: internal/filter ] (コスト 0 円)                  |
|       ├── Stage 1: メディア必須判定 (添付画像 1枚以上)                            |
|       │      └── テキストのみの日常ツイート、単純リポストを 90% 除外              |
|       ├── Stage 2: ライブ告知キーワード照合                                       |
|       │      └── 「開場」「開演」「特典会」「タイテ」「チケット」等の合致を要求   |
|       └── Stage 3: 重複・既知セッション排除                                       |
|              └── 既存 raw/runs/ または schedule.json 登録済みポストを即座に破棄   |
|                                                                                   |
|       ▼ (フィルターを通過した 1〜2件のみ)                                        |
|  [ 送信クライアント: internal/source/x ]                                          |
+-------│---------------------------------------------------------------------------+
        │ (HTTPS POST / Bearer Token)
        ▼
+-----------------------------------------------------------------------------------+
| Google Cloud Run (taite-parser)                                                   |
|                                                                                   |
|  [ Gemini 2.5 Flash Vision ]                                                      |
|       └── フライヤー・タイテ画像の OCR 解析および本文との名寄せ構造化             |
|       └── 出力: candidate JSON (ADR-0001 準拠の候補データ)                        |
+-------│---------------------------------------------------------------------------+
        │ (レスポンス返却)
        ▼
+-----------------------------------------------------------------------------------+
| 自宅 Kubernetes Ceph RBD PVC (永続ストレージ)                                     |
|                                                                                   |
|  [ 保存先: data/candidate/<run_id>.json ]                                         |
|       └── 証跡・生テキスト・抽出データを完全保持                                  |
|                                                                                   |
|  [ 人間レビュー & 昇格: taite promote <run_id> ]                                  |
|       ├── 1. JSON Schema (Draft-07) 厳格バリデーション                            |
|       ├── 2. 同日複数公演のインターバル重複検査 (ADR-0014)                        |
|       ├── 3. data/generated/schedule.json への時系列自動マージ                    |
|       └── 4. Web 公開ターゲットへの自動同期 (verify.sh / GitOps PR)              |
+-----------------------------------------------------------------------------------+
~~~

## 2. コンポーネント詳細設計

### 2.1 ヘッドレスクローラー (`internal/crawler` / `deploy/crawler`)

X の SPA 仕様に対抗しつつ、外部 SaaS に依存しない自前クローラーを構築する。

- **技術選定**: Node.js + Playwright (Headless Chromium)
- **実行形態**: Kubernetes `CronJob`（常時稼働ではなく、実行時のみ Pod を起動して終了する Scale-to-Zero 設計）
- **巡回スケジュール**: `0 3,13 * * *` (UTC) = 日本時間 12:00, 22:00（1日2回）
- **取得プロトコル（GraphQL インターセプト）**:
  DOM の HTML 要素（セレクタ）を走査するのではなく、ブラウザがバックグラウンドで発行する以下の通信を監視する。
  - URL パターン: `https://x.com/i/api/graphql/*/UserMedia*`
  - 取得データ:
    - `rest_id` (ポスト ID)
    - `legacy.full_text` (ポスト本文)
    - `legacy.entities.media` (画像 URL 配列 `pbs.twimg.com/media/...`)
    - `legacy.created_at` (投稿日時)
  - **利点**: X の UI デザイン変更や CSS クラス名変更の影響を一切受けず、公式の生 JSON データを取得可能。

### 2.2 多段ローカル前処理フィルター (`internal/filter`)

Cloud Run / Gemini 2.5 Flash Vision への不要な呼び出しを徹底的に阻止する。

| 段階 | 検査項目 | 合格条件 | 破棄対象（具体例） |
|---|---|---|---|
| **Stage 1** | 添付メディア数 | `len(images) >= 1` | テキストのみの日常ツイート、告知のない写真なし投稿 |
| **Stage 2** | 告知キーワード | 必須キーワード群から 1 件以上合致、かつ除外キーワードに非該当 | グッズ通販告知、チェキ券販売告知、単なるお礼ツイート |
| **Stage 3** | 重複検査 | 未処理の `status_id` であり、かつ `schedule.json` に未登録の公演 | 過去の告知の再掲・リマインド、同一イベントの引用RT |

#### キーワード定義テーブル

```go
type FilterRules struct {
    // 必須キーワード（いずれか1つ以上を含むこと）
    RequiredKeywords []string
    // 除外キーワード（含まれている場合は即時破棄）
    NegativeKeywords []string
}

var DefaultRules = FilterRules{
    RequiredKeywords: []string{
        "ライブ情報", "出演情報", "タイムテーブル", "タイテ",
        "開場", "開演", "特典会", "出番", "チケット",
        "TicketDive", "LivePocket", "TIGET", "tiget",
    },
    NegativeKeywords: []string{
        "通販", "オンラインショップ", "生誕グッズ", "受注生産",
        "完売御礼", "おやすみ", "おはよう", "ブロマイド",
    },
}
```

### 2.3 昇格エンジン (`cmd/taite promote`)

自動生成された `data/candidate/<run_id>.json` を、安全に本番の `data/generated/schedule.json` へ取り込む Go CLI サブコマンド。

1. **入力**: `taite promote <run_id>`（または `taite promote --interactive`）
2. **検証プロセス**:
   - `candidate` ファイルの存在と破損チェック
   - 抽出されたセッションデータに対する `schema/schedule.schema.json` 適合検査
   - 既存セッションとの重複検査（同一日・同一タイトル）
   - 同日複数セッション時の出番・特典会時間重複検査（ADR-0014 準拠）
3. **反映プロセス**:
   - `data/generated/schedule.json` の `sessions` 配列へ追加（同一 ID があれば更新）
   - 日付および開始時刻による時系列ソート
   - `generated_at` の現在時刻更新
   - `apps/web/public/` 配下の公開コピーへの自動同期
4. **差分サマリー出力**:
   - 追加・更新された公演タイトル、出番時刻、会場名、チケット代をターミナルにプレビュー表示。

## 3. コスト・計算量・クォータ防衛策

### 3.1 Cloud Run & Gemini API 呼び出し頻度
- 公式アカウントの平均投稿数: 1日 約 3〜5 件
- Stage 1（画像必須）通過率: 約 40%（1日 1〜2 件）
- Stage 2（キーワード判定）通過率: 約 25%（1日 0.5〜1 件）
- Stage 3（重複排除）通過率: 約 10〜20%（新規告知のみ通過）
- **最終的な Cloud Run 呼び出し回数: 1日 0.5〜1.5 回（月間 15〜45 回）**
- **月間 API 費用試算: 約 0.01〜0.02 ドル（約 1.5〜3 円、Google Cloud 無料枠内で 100% 収容）**

### 3.2 X へのアクセス負荷と遮断防止
- 巡回間隔: 1日 2 回（12:00, 22:00）
- 1回の巡回における通信量: メディアタブの初期表示（1リクエスト）のみ
- 連続スクロールや大量ページネーションは行わず、直近 10 件のメディアのみを検査
- ユーザーエージェント、Viewport、言語設定（`ja-JP`）を正規の macOS Chrome 環境と一致させて偽装

### 3.3 冪等性とキャッシュキー（無駄な AI 再解析の完全抑止）

Cloud Run への呼び出し判定において、入力ポストの指紋（`raw_fingerprint`）および解析仕様ハッシュ（`parse_cache_key`）を算出し、完全に同一の入力・同一のプロンプトバージョンの場合はローカルキャッシュ（`data/candidate/`）を再利用して HTTP リクエスト自体を発生させない。

~~~text
raw_fingerprint = SHA-256(
  source
  + source_id
  + normalized_text
  + ordered_media_sha256_list
)

parse_cache_key = SHA-256(
  raw_fingerprint
  + candidate_schema_version
  + parser_version
  + model_id
  + prompt_version
)
~~~

同一 `parse_cache_key` の候補ファイルが既に存在する場合、AIパーサーをスキップして既存の candidate を即時再利用する。パーサーやモデル・プロンプトのバージョンが更新された場合のみキーが変化し、必要最小限の再解析が行われる。

## 4. ベテランエンジニア観点によるセルフレビュー (System Design Review)

`.agents/rules/system-design-review.md` および `AGENTS.md` の原則に基づき、設計のセルフレビューを実施した。

### 4.1 単一障害点 (SPOF) と耐障害性の評価
- **課題**: X 側の GraphQL エンドポイントの変更や、自宅のネットワーク一時切断時に何が起きるか？
- **評価**:
  - クローラーは非同期の CronJob であるため、クローラーが一時的に失敗しても、配信中の Web アプリ（Ribbon Clock）や既存の `schedule.json` には一切影響を与えない。
  - 万が一クローラーが停止した場合でも、既存の Tailscale 手動 Intake ダッシュボードが完全にフォールバックとして機能し続ける。

### 4.2 オーバーエンジニアリングの有無
- **課題**: 独自 DB や常時稼働マイクロサービスの導入を避けているか？
- **評価**:
  - PostgreSQL や Redis などのミドルウェアは一切追加せず、永続化はすべて「既存の Ceph RBD PVC 上の JSON ファイル」で完結している。
  - クローラー自身も常時メモリを食う Deployment ではなく、実行後数秒で消滅する CronJob としており、極小リソースで成立している。

### 4.3 人間と AI の責任分界点 (Human-in-the-Loop)
- **課題**: AI が誤ってタイテを読み違えた場合に本番画面へ誤情報が流出しないか？
- **評価**:
  - クローラーの出力先を `candidate` に厳格に限定し、`schedule.json` への昇格には必ず `taite promote`（人間による確認・実行）を介在させている。
  - これにより、AI の幻覚（ハルシネーション）や OCR 誤読による誤情報の自動公開を 100% 防御できる。

### 4.4 結論
本設計は最小の複雑性とコストで最大の自動化効果を達成しており、破綻要因のない実用的なアーキテクチャであると判断する。
