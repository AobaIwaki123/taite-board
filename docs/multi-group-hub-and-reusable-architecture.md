# マルチグループ展開・機能再利用および推し活コンパニオンアプリ設計構想

## 1. 文書の位置づけ

本ドキュメントは、単一アイドルグループ（RiNCENT#）向けに最適化された Ribbon Clock（`taite-board`）の設計資産を整理し、以下の3つの拡張に向けたアーキテクチャ境界とロードマップを定義するものである。

1. **設計の再利用性とマルチグループ展開（Hub Portal 構想）**
   - 共通ドメインロジック・コンポーネントのモジュール化
   - グループごとのサブドメイン運用（`*.iorin.net`）とポータルハブ（`hub.iorin.net` 等）
   - 新規グループ追加をテンプレート複製・最小設定で完結させる基盤
2. **チェキツイ・特典会レポ管理アプリケーション構想**
   - 撮影済みチェキの整理、ツイート済み／下書きステータス管理
   - メンバータグ・公式ハッシュタグの自動付与と事故防止
   - 完全ローカル完結型によるプライバシーと著作権リスクの完全排除
3. **推し活SNS利用制限・自律管理アプリケーション構想（iOSネイティブ）**
   - 衝動的な長時間のX巡回・深夜投稿の抑制
   - 現場スケジュール連動型（特定時間枠のみ解放）の行動制御
   - iOS Screen Time API（FamilyControls / ManagedSettings）の活用

## 2. taite-board 設計資産の棚卸しと再利用可能モジュール

現行の `taite-board` は、単なる画面実装にとどまらず、アイドル現場特有の複雑な時間軸や支出構造を堅牢に扱うコアロジックを保有している。これらをUI層から分離することで、他グループ向け展開や新規ツール開発へ即座に転用できる。

### 2.1 共通コアロジック（UI非依存の純粋関数群）

以下のユーティリティ群（`apps/web/src/utils/`）は、DOMやUIフレームワーク（Preact）に依存しない純粋な TypeScript ロジックであり、100%単体テスト（`npm test`）で保護されている。

| モジュール | 主な提供機能 | 他アプリ・他グループへの再利用性 |
|---|---|---|
| `date.ts` | `isSessionPast`（終演即座判定）<br>`resolveNextSession`（直近・次回公演自動昇格）<br>`getSessionProgress`（ライブ・特典会カウントダウン） | 任意のライブスケジュールアプリ・通知bot・タイムライン管理でそのまま流用可能 |
| `expense.ts` | `parseTicketFee`（ドリンク代注記除去・金額抽出）<br>`isIncrementalFee`（差額表記検知）<br>`calculateMonthExpenseSummary`（週・月別支出集計） | チケット管理、家計簿、チェキ出費計算ツールへ無修正で組み込み可能 |
| `freshness.ts` | データの鮮度判定、オフラインキャッシュ警告メッセージ生成 | 静的JSON配信を行うすべてのPWA・クライアントで共通利用可能 |
| `deadline.ts` | チケット発売日・予約締切カウントダウン判定 | 申込アラート機能やカレンダー連携で共通利用可能 |

### 2.2 UIコンポーネントのテンプレート化

画面層（`apps/web/src/components/`）は、状態管理とプレゼンテーションが整理されているため、テーマ設定（カラーパレット、ロゴ、フォント）の注入によって他グループ画面を即時生成できる。

- **CockpitView**: 「いま・つぎ」に特化した計器盤。グループのテーマカラー（Primary/Accent）を props で差し替え可能。
- **CalendarView**: 月間カレンダー＋収支サマリー＋週別内訳。
- **ListView**: 時系列順の全公演リスト。
- **ExpenseMemoCard**: LocalStorage による現場完結の支出・チェキ枚数メモ。

## 3. マルチグループ展開とハブポータル設計（*.iorin.net）

将来的に複数グループのスケジュールを管理・横断検索可能にするためのシステム構成案。

### 3.1 ドメイン・ルーティング構成

単一のトップポータルと、グループごとの独立サブドメインを疎結合に配置する。

~~~text
[ ユーザー / ブラウザ ]
        │
        ├── hub.iorin.net / iorin.net (ポータル・横断検索ハブ)
        │     ├── 全グループ本日の現場レーダー（横断タイムライン）
        │     ├── グループ選択カード一覧
        │     └── 横断カレンダー（推し増し・複数現場巡回支援）
        │
        ├── rincent.iorin.net (RiNCENT# 専用 Ribbon Clock)
        │     └── data/groups/rincent/schedule.json
        │
        ├── <group-slug>.iorin.net (別グループ専用ボード)
        │     └── data/groups/<group-slug>/schedule.json
~~~

### 3.2 なぜ「単一の巨大DB」ではなく「グループ単位の独立データ」にするのか

1. **障害の局所化**:
   - アイドル運営ごとに公式Xの告知書式、TicketDive / LivePocket 等の利用プラットフォーム、タイテ画像の解像度が全く異なる。
   - 1つのグループのパース失敗や告知形式変更が、他グループのスケジュール配信に一切波及しない構造を死守する。
2. **インフラの極小コスト運用**:
   - 各グループの出力は静的 `schedule.json` のみ。Cloudflare Pages や既存の自宅 K8s / Nginx 静的配信に載せるだけであり、月額サーバー費用がグループ数に比例して跳ね上がることがない。
3. **新規グループ追加の自動化（スキャフォールディング）**:
   - `./scripts/new-group.sh <group-slug> "<グループ名>"` を実行することで、専用のデータディレクトリ、テーマ設定、ビルド設定が即時生成される構成を目指す。

## 4. チェキツイ・特典会レポ管理アプリケーション構想

### 4.1 背景と解決したい課題

- **写真の埋没と投稿漏れ**: 週末に複数公演・複数メンバーと撮影したチェキ写真が iPhone の写真ライブラリに埋もれ、「どれをツイート済みで、どれが未投稿か」が分からなくなる。
- **誤タグ・誤爆防止**: メンバーのXアカウントIDや公式ハッシュタグを手動入力すると、誤字や付け忘れが発生しやすい。
- **会話レポの記録**: 特典会直後の記憶が鮮明なうちに、話した内容（レポ）や衣装の感想をチェキ画像と1対1で紐づけて下書きしたい。

### 4.2 機能要件

1. **チェキカードの作成**:
   - カメラ撮影または写真ライブラリからのチェキ画像取り込み。
   - メンバー選択（登録済みメンバーリストからワンタップ）。
   - 撮影日・部数・衣装メモの入力。
2. **ツイート下書きエディタ**:
   - メンバーメンション（`@xxx`）と公式タグ（`#xxx`）を自動挿入。
   - 文字数カウント（日本語140字 / 全角半角判定）。
   - 会話レポ（吹き出し形式またはテキスト）のメモ欄。
3. **ステータス管理**:
   - `下書き` / `投稿待ち` / `投稿完了` のステータス管理。
   - ワンタップで公式Xアプリの投稿画面を起動（画像添付＋本文コピー）。
4. **プライバシーと著作権のゼロリスク性**:
   - 個人が撮影した私物チェキ写真のみを扱うため、外部著作権を侵害しない。
   - サーバーへの画像アップロードは一切行わず、端末内（Local Sandbox）で100%完結。

## 5. 推し活SNS利用制限・自律管理アプリケーション構想（iOSネイティブ）

### 5.1 背景と課題意識

- 推し活においてXは必須の情報収集・交流ツールである反面、タイムラインの無限巡回、深夜の無意識な閲覧、衝動的なポストなど、自己制御を失いやすい側面を持つ。
- 通常のWebアプリやブラウザ拡張では、ネイティブアプリ（公式Xアプリ等）の起動や利用時間を制限することはOSのサンドボックス上不可能である。

### 5.2 なぜ iOS ネイティブ（SwiftUI）でリベンジする価値があるのか

スケジュール表示のiOSアプリ化（旧 `apps/ios/`）は、Web（PWA）との二重保守コストを理由に凍結（ADR-0011）された。しかし、**チェキツイ管理およびSNS利用制限は、Webでは技術的に実現不可能な「OSネイティブ固有の領域」**である。

| 領域 | Web (PWA) | iOS ネイティブ (SwiftUI) | 判断 |
|---|---|---|---|
| 公演スケジュール表示 | 最適（即時更新・共有容易） | 二重保守になり不適 | Web（Ribbon Clock）に一本化 |
| チェキ撮影・写真管理 | ブラウザ経由（制限あり） | Photos / Camera 連携が快適 | ネイティブ向き |
| Xアプリの起動・時間制限 | **実現不可**（サンドボックス外） | **実現可能**（Screen Time API） | **ネイティブ必須** |

### 5.3 iOS Screen Time API を用いた実装アーキテクチャ

iOS 15 / 16 以降で公開されている Apple 公式の Screen Time API 群を活用する。

1. **FamilyControls**:
   - 端末利用者自身の認可（Individual Authorization）を取得し、制限対象アプリ（X、ブラウザ等）の選択UI（`FamilyActivityPicker`）を表示。
2. **ManagedSettings**:
   - `ManagedSettingsStore` を通じて、特定アプリのシールド（起動禁止画面）を有効化／無効化。
3. **DeviceActivity**:
   - スケジュールされた時間枠（例: 23:00〜翌朝07:00の深夜帯、または平日の日中作業時間）を監視し、イベント発火時に自動でシールドを適用。

### 5.4 現場連動型の制限解除（スケジュール連携）

単なる機械的な時間制限にとどまらず、Ribbon Clock のデータと組み合わせた高度な自律制御が可能になる。

- **チェキツイ投稿ウィンドウ**:
  - 特典会終了後の1時間（例: 21:00〜22:00）のみ、チェキツイ投稿のためにXのシールドを自動解除。
- **投稿摩擦（クーリングオフ）**:
  - 衝動的なポストを防ぐため、チェキツイ管理アプリで下書きをレビュー・セルフチェックしてからでないと投稿画面へ進めない動線を確保。

## 6. 今後の進め方とロードマップ

1. **Phase 1: ドキュメント化とアーキテクチャ整理（本フェーズ）**
   - 共通モジュール・テンプレート境界の定義。
   - チェキツイ管理およびSNS制限アプリの要件定義の固定。
2. **Phase 2: チェキツイ・自律管理 iOS アプリのプロトタイプ（`apps/oshikatsu-companion/` 等）**
   - SwiftUI + SwiftData によるチェキ管理ローカルアプリの作成。
   - Screen Time API（FamilyControls）によるX起動制限の技術検証（PoC）。
3. **Phase 3: マルチグループ・ポータルハブの検討**
   - Ribbon Clock テンプレートの抽出（`packages/schedule-core` 等）。
   - `hub.iorin.net` のプロトタイプ設計。
