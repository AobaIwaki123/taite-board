# プライバシー配慮型アクセス回数集計設計

## ステータス

Proposed

## 目的

Ribbon Clock の利用状況を、個人を識別せずに運用上把握する。必要な情報は「どの時間帯に、配信サーバーへ何件のリクエストが到達したか」であり、ユーザー単位の追跡や行動分析ではない。

初期実装では、ブラウザや iOS アプリに計測コードを追加せず、Nginx のサーバーアクセスログを端末上のスクリプトで必要なときだけ集計し、結果を Discord へ通知する。

## 1. 要求と非要求

### 要求

- JST の1時間単位でアクセス回数を確認できる。
- 必要なときだけスクリプトを実行し、Discord に集計結果を送信できる。
- 同じ期間を何度集計しても二重計上しない。
- 取得元、URL、IPアドレス、User-Agent、Cookie を集計結果から復元できない。
- 現行の「クライアント側でトラッキングしない」方針を維持する。

### 非要求

- ユニークユーザー数、リピーター数、セッション数の推定
- 個人・端末・IPアドレス単位の追跡
- ページ内のクリック、滞在時間、画面遷移の計測
- Cloudflare のキャッシュヒットを含む全エッジアクセスの把握
- 初期段階でのダッシュボードや常時稼働する分析基盤
- 自分用の管理ダッシュボード。必要性と運用方法を検討中であり、初期実装には含めない

## 2. 現状認識

- 配信は Kubernetes 上の Nginx が担当し、外部公開は Cloudflare Tunnel 経由で行っている。
- `/healthz` は現在アクセスログを無効化している。
- その他のパスについて、`deploy/nginx.conf` にはプライバシー制約を明示した `log_format` がない。
- クライアントにはアクセス解析 SDK や識別用 UUID を追加しない方針がある。

そのため、最初に Nginx のログ形式を変更し、既定の combined log が持ち得る IP や User-Agent を出さないことを必須とする。集計スクリプトだけを追加しても、入力ログに不要な情報が残っていれば目的を満たさない。

Nginx のベースイメージが `http` コンテキストで既定の `access_log` を設定している場合、匿名ログを追加するだけでは既定ログが併記される可能性がある。匿名 `access_log` は対象 `server` コンテキストへ明示し、既定の combined log を継承しないことをコンテナで確認する。

## 3. 採用案

### 3.1 Nginx は匿名化した構造化ログだけを標準出力へ出す

ログはリクエストごとに1行出力するが、次の最小項目だけに限定する。

```json
{"ts":"2026-10-30T14:23:05+09:00","route":"document","status":200}
```

出力項目は次のとおりとする。

| 項目 | 内容 |
| --- | --- |
| `ts` | Nginx が受け付けた時刻。集計時に `Asia/Tokyo` へ変換する |
| `route` | 生 URL ではなく、固定のルート分類 |
| `status` | HTTP ステータスコード。集計時に `2xx` などへまとめる |

記録しない項目は `remote_addr`、`remote_user`、`request`、`request_uri`、`args`、`http_user_agent`、`http_referer`、Cookie、Authorization ヘッダーとする。特に `$request_uri` と `$args` はクエリ文字列を含み得るため使用しない。

### 3.2 ルート分類は固定値に限定する

URLそのものを Discord や集計ファイルへ渡さない。Nginx の `$uri` を次の固定分類へ写像する。

| 分類 | 対象 |
| --- | --- |
| `document` | `/`、`/index.html` |
| `schedule` | `/schedule.json`、`/mock_schedule.json` |
| `asset` | `/assets/`、`/icons/`、`/images/` 配下 |
| `other` | 上記以外 |
| `health` | `/healthz`。ログ出力しない |

この分類は、パス名に含まれる ID やクエリの収集を避けるため、未知のパスをすべて `other` にまとめる。

### 3.3 集計は必要なときだけ実行する

自宅サーバーまたは管理端末から、指定期間の Kubernetes ログを読み取る。初期段階では集計結果を常時保存せず、指定された期間を毎回再集計する。

想定するインターフェースは次のとおりとする。

```bash
scripts/report-access-counts.sh \
  --from 2026-10-30T00:00:00+09:00 \
  --to 2026-10-31T00:00:00+09:00 \
  --dry-run
```

`--dry-run` では Discord へ送らず、送信予定の集計メッセージだけを端末へ表示する。確認後、同じ期間を指定して Webhook 送信する。

```bash
DISCORD_WEBHOOK_URL='環境変数から注入' \
  scripts/report-access-counts.sh \
    --from 2026-10-30T00:00:00+09:00 \
    --to 2026-10-31T00:00:00+09:00
```

スクリプトは `[from, to)` の閉区間ではなく、開始を含み終了を含まない半開区間として扱う。これにより、隣接する期間を指定しても境界時刻を二重に数えない。

### 3.4 Discord へ送るのは集計結果だけにする

送信メッセージには対象期間、生成時刻、分類別の件数、ステータス分類別の件数だけを含める。

```text
Ribbon Clock アクセス集計
対象: 2026-10-30 00:00〜24:00 JST
種別: origin request count

合計: 184
- document: 42
- schedule: 37
- asset: 96
- other: 9

status:
- 2xx: 180
- 4xx: 3
- 5xx: 1
```

Discord Webhook URL、raw log、元 URL、個別時刻、IP、User-Agent、リクエスト本文は送信しない。

## 4. 二重計上を防ぐ方法

集計スクリプトは「前回実行時のカウンターへ加算」しない。毎回、指定された期間の raw log からスナップショットを再計算する。

同じ期間を再実行した場合、ログ保持期間と Pod の存続状態が同じなら同じ集計値になる。Discord には対象期間を明記するため、同じ期間の再通知も重複集計ではなく再確認として扱える。

将来、日次・月次の履歴を保存する必要が生じた場合は、`bucket_start`、`route`、`status_class`、`count` だけを SQLite または JSON に保存する。リクエスト単位の raw log を永続保存する設計へは拡張しない。

## 5. 保持期間と秘密情報

### raw log

- raw log は Kubernetes のコンテナログとして短期間だけ保持する。
- 初期値は24時間を目安とし、kubelet / ノード側のログローテーション設定も同じ方針に合わせる。
- 集計処理が失敗しても、IP 等を含まないため再取得できるが、保持期間を超えた期間は欠測として扱う。

### 集計結果

- Discord に通知した集計値は、運用上必要な期間だけ残す。
- リポジトリの公開ディレクトリや `data/generated/` には保存しない。
- 履歴が必要になった場合も、匿名集計値のみを自宅サーバーの非公開領域へ保存する。

### Webhook

- `DISCORD_WEBHOOK_URL` はリポジトリへ保存しない。
- 自宅サーバーの環境変数、Secret 管理、または権限を限定した設定ファイルから注入する。
- コマンド引数に直接 URL を渡さず、シェル履歴やプロセス一覧への露出を避ける。

## 6. 制約とトレードオフ

### origin request 数に限定する

Nginx で数えられるのは、Cloudflare のキャッシュや中間キャッシュを通過して origin へ到達したリクエストだけである。Cloudflare 側で応答されたキャッシュヒットは含まれない。

これは「実際の閲覧者数」ではなく「自宅 Kubernetes へ届いたリクエスト数」である。全エッジアクセスを計測するには Cloudflare のログ連携が必要になるが、取得できる情報と運用負担が増えるため初期案では採用しない。

### リクエスト数に限定する

アプリ起動、PWA のバックグラウンド更新、iOS アプリの再取得は、同じ利用者でも複数リクエストとして数えられる。個人を推定するための補正や deduplication は行わず、数値の意味を「origin request count」と明記する。

### 手動実行に限定する

常時稼働する集計サービスやダッシュボードを用意しないため、リアルタイム性と長期履歴は得られない。一方で、実装・監視・外部送信の頻度を最小限にできる。アクセス状況を定期観測したくなった段階で、まず集計済みバケットの保存だけを追加する。

## 7. 実装フェーズ

### Phase 1: ログ形式と dry-run

1. `deploy/nginx.conf` に固定ルート分類と匿名 JSON log format を追加する。
2. `/healthz` を除くリクエストが JSON Lines になることを確認する。
3. `report-access-counts` は標準入力または `kubectl logs` の出力を受け取り、dry-run で集計結果を表示する。
4. fixture に IP、User-Agent、クエリ文字列が含まれていても、出力へ伝播しないことをテストする。

### Phase 2: Discord Webhook

1. dry-run と同じ集計値を Webhook へ送る。
2. Webhook URL が未設定の場合は送信せず、エラーを明示する。
3. HTTP エラー時は raw log や Webhook URL を出力せず、再実行可能な終了コードを返す。
4. 実際の Discord チャンネルへ送るのは、少量の fixture で payload を確認した後にする。

### Phase 3: 必要になった場合だけ履歴保存

1. 日次または月次の集計値だけを非公開領域へ保存する。
2. 保存対象は時間バケット、分類、ステータス分類、件数に限定する。
3. 保存期間と削除方法を決めるまでは、Discord 通知だけで運用する。

### 管理ダッシュボードは別途検討

管理ダッシュボードを追加する場合も、Nginx の raw log を直接表示・検索する構成にはしない。Phase 3 で保存する匿名集計値だけを読み取り、自宅 LAN 内からのみ到達できる構成とする。次の制約を引き継ぐ。

- `kubectl port-forward` による localhost 公開、または自宅 LAN のファイアウォールで制限した管理用アドレスを使用する。
- Cloudflare Tunnel、公開 Ingress、LoadBalancer、公開ドメインには接続しない。
- 認証を追加し、公開サイトと同じ公開経路へ置かない。LAN 内限定でも認証を省略しない。
- 時間バケット、分類、ステータス、件数だけを表示する。
- Discord 通知と同じ集計値を表示し、ダッシュボード導入後も手動スクリプトを障害時の確認手段として残す。

この方針により、Discord は初期の軽量な集計通知、ダッシュボードは必要性が確認された後の LAN 限定表示先として、同じ集計契約を共有できる。LAN 外からのリモートアクセスは別途のセキュリティ判断が必要なため、現設計では提供しない。

## 8. 完了条件

- クライアントコードに計測処理、Cookie、識別子を追加していない。
- Nginx のログに IP、User-Agent、Referer、Cookie、クエリ文字列が出ない。
- `healthz` の probe が集計値を増やさない。
- 同一期間の再集計で累積二重計上が起きない。
- dry-run の出力に URL、IP、User-Agent、Webhook URL が含まれない。
- Discord へ送るメッセージが時間帯・分類・件数だけで構成される。
- Cloudflare キャッシュを含まない origin request count であることが、運用手順と通知文に明記される。
- 管理ダッシュボードを実装する場合、localhost または自宅 LAN からのみ到達でき、公開 Ingress や Cloudflare Tunnel に接続されていない。
- [privacy-policy.html](../apps/web/public/privacy-policy.html) の「運用目的の匿名集計」への記載変更を、実装の公開前に行う。

## 9. 採用しなかった案

| 案 | 採用しない理由 |
| --- | --- |
| ブラウザから計測 API を呼ぶ | クライアント計測、識別子、失敗時の再送制御が必要になり、Zero Telemetry 方針と運用負担に反する |
| IP のハッシュを保存する | ユニーク数は得られるが、再識別・辞書攻撃・保持期間の管理が必要になる |
| Cloudflare の詳細ログを常時取り込む | origin 外のアクセスは見えるが、取得情報・外部依存・保管責任が増える |
| Prometheus / Grafana を導入する | 現在の「必要なときだけ Discord へ出す」という目的に対して常時稼働コンポーネントが過剰 |
| リクエスト単位の SQLite 保存 | 集計目的に不要なデータを永続化し、削除・アクセス制御の負担が増える |
